Menurut saya, pendekatan terbaik adalah **hybrid**:

| Kondisi class | Perlakuan |
|---|---|
| Ada padanan setting | Konversi ke setting widget |
| Tidak ada padanan | Simpan ke `CSS Classes` |
| Ada `id` asli | Simpan ke `CSS ID` |
| Class framework | Muat dependency framework yang sudah diizinkan |
| CSS custom dari `<style>` | Scoped CSS atau tampilkan sebagai warning |

Yang perlu diluruskan: semua class masuk ke **CSS Classes**, bukan CSS ID. CSS ID hanya untuk satu `id` unik. Jangan membuat ID palsu dari nama class.

Namun, class fallback tidak cukup untuk layout utama. Class seperti `grid`, `grid-cols-3`, `.row`, dan `.col-md-6` tetap harus dikonversi ke struktur canonical `container`, `gridColumns`, `columns`, dan responsive settings. DOM Canvas berbeda dari HTML asli, sehingga class `grid` yang ditempel pada wrapper widget belum tentu mengatur elemen internal Canvas dengan benar.

CDN bisa menjadi fallback yang bagus, tetapi:

- Bootstrap dapat memakai CSS CDN yang versinya dipin.
- Tailwind bukan sekadar `<link>` CSS; konfigurasi seperti `tailwind.config` perlu ditangani secara aman.
- Pada CEO Masters, class seperti `bg-ink`, `text-cream`, `gold-button`, `feature-card`, dan `hero-frame` berasal dari konfigurasi/CSS custom. CDN Tailwind saja tidak akan mengembalikannya.
- Dependency harus tersedia di Canvas dan frontend renderer, serta disimpan sebagai metadata halaman. Jangan menjalankan script atau URL arbitrary dari file import.

Jadi, kita tidak perlu menunggu sampai seluruh ribuan class Tailwind/Bootstrap selesai dipetakan. Urutan paling masuk akal:

1. Perbaiki struktur layout dan responsive grid.
2. Pertahankan class serta ID asli ke control seperti pada screenshot.

- paling stabil;
- hasil CSS bisa disimpan langsung;
- tidak bergantung CDN ketika halaman dibuka;
- cocok untuk production;
- tidak perlu mempertahankan class Tailwind.

Kekurangan:

- perlu menyediakan Tailwind compiler yang sesuai versi sumber;
- harus menangani konfigurasi Tailwind dan plugin yang digunakan.

```text
DOM asli + Tailwind CDN

Tailwind membuat <style>
        ↓
CSS dari <style> dibaca
        ↓
CSS disimpan
        ↓
Class Tailwind dihapus
        ↓
CDN Tailwind dibuang
```

Kelebihannya tidak perlu memasang compiler lokal tambahan. Namun, prosesnya lebih kompleks karena kita harus menunggu Tailwind selesai membuat CSS dan kemudian menulis ulang selector class menjadi selector node Page Builder.

Untuk proyek kita, saya lebih merekomendasikan opsi hybrid:

```text

2. Konversi layout ke widget native
3. Mapping CSS ke setting widget jika tersedia
4. Simpan CSS yang belum memiliki setting sebagai compiled scoped CSS
5. Jika proses compile gagal, tetap gunakan Exact Visual iframe sebagai fallback
```

Struktur akhirnya bisa seperti ini:

```text

├── Native Page Builder Layout
├── Widget settings

├── Custom semantic CSS
└── Exact Visual fallback
```

Namun JavaScript berbeda dengan CSS: CSS relatif aman untuk disimpan dan dijalankan, sedangkan JavaScript arbitrary dapat:

- mengirim request ke server;

- menjalankan kode berbahaya.

Arsitektur yang aman:

```text

├── Compiled Native

│   ├── CSS final disimpan di Custom CSS
│   └── JavaScript sumber tidak dijalankan
│
├── Exact Visual Sandbox
│   ├── DOM asli dipertahankan
│   ├── Custom JavaScript dapat dijalankan di iframe sandbox
```

- `Compiled Native`: JavaScript sumber tidak dijalankan.
- `Exact Visual`: JavaScript sumber dapat dipertahankan di dalam iframe sandbox.

```text
#menu-toggle pada HTML asli
≠
struktur DOM widget Page Builder
```

```json

  "action": "toggle",

}
```

1. Menyimpan di field `custom_js` baru pada tabel page builder, sama seperti `custom_css`.
2. Untuk tahap awal yang lebih aman, menyimpan di `settings.staticImport.customJs` pada node `static_html`.

Saya merekomendasikan tahap awal:

```text
Exact Visual
└── sourceHtml + sourceScripts + sourceCss di dalam static_html
```

```text

```

Kesimpulannya: ya, sangat memungkinkan dan tepat dibuat khusus seperti Custom CSS. Tetapi `Custom JavaScript` sebaiknya menjadi fallback untuk `Exact Visual Sandbox`, bukan mekanisme untuk memaksa JavaScript arbitrary bekerja pada layout native.

Betul, nested `div` harus bisa dideteksi secara recursive, berapa pun kedalamannya. Jadi konsepnya jangan diartikan sebagai “semua child digabung lalu disembunyikan”.

Yang lebih tepat adalah tiga lapisan:

```text
Raw DOM node
└── seluruh element asli: div, span, img, i, p, h1, dan lainnya

Structural group
└── div yang mengatur grid, flex, padding, background, border, ukuran, posisi

Mapping block
└── kelompok visual yang akan dipetakan ke widget tertentu
```

Contoh HTML:

```html
<div class="card">
  <div class="media">
    <img src="photo.jpg">
  </div>

  <div class="content">
    <h3>Title</h3>
    <p>Description</p>
  </div>
</div>
```

Mesin tidak boleh melihatnya sebagai daftar datar:

```text
div
div
img
div
h3
p
```

Tetapi sebagai tree:

```text
Card div
├── Media div
│   └── Image
└── Content div
    ├── Heading
    └── Text
```

Lalu mesin menganalisis dari bawah ke atas:

1. `img` dikenali sebagai Image.
2. `h3` dikenali sebagai Heading.
3. `p` dikenali sebagai Text Editor.
4. `content div` dikenali sebagai Container vertikal.
5. `card div` dianalisis lagi:
   - jika komposisinya cocok dengan Image Box, diberi kandidat Image Box;
   - jika tidak, tetap menjadi Container dengan child Image, Heading, dan Text Editor.

Jadi `div` akan dianggap sebagai composite widget hanya jika:

- memiliki kelompok child yang saling berhubungan secara visual;
- memiliki padding, background, border, gap, atau ukuran sebagai satu kesatuan;
- child-nya membentuk pola seperti icon + title + description atau image + title + description;
- struktur tersebut dapat direpresentasikan oleh widget yang tersedia.

Kalau sebuah `div` memiliki nested layout yang penting, misalnya Grid di dalam Flex, maka tidak boleh dipaksa menjadi satu widget. Struktur tersebut tetap dipertahankan:

```text
Container/Flex
└── Container/Grid
    ├── Column 1
    └── Column 2
```

Untuk screenshot Anda:

```text
Metadata div
├── dt
│   ├── icon
│   └── Date
└── dd
    └── 10 October 2026
```

Mapping utamanya bisa menjadi:

```text

```

Tetapi `dt`, icon, dan `dd` tetap disimpan sebagai member. Jika Icon Box ternyata tidak cukup akurat, user bisa memilih:

```text

└── Container
    ├── Icon
    ├── Text Editor
    └── Text Editor
```

Jadi arti “satu visual composition = satu source block” adalah satu baris mapping mewakili satu unit visual, bukan menghapus child DOM. Supaya tidak membingungkan, saya menyarankan istilah UI-nya diganti menjadi:

- `Raw DOM elements`
- `Structural groups`
- `Visual mapping blocks`
- `Nested members`

Dengan model ini, mesin tetap membaca semua nested `div`, tetapi tidak memaksa setiap `div`, `span`, atau `i` menjadi widget terpisah.

Kesimpulannya: ya, kita bisa dan memang harus mendeteksi nested `div` secara recursive, menggunakan analisis bottom-up, lalu menentukan apakah parent tersebut adalah Container, Image Box, Icon Box, atau hanya structural wrapper.

- kolom berubah;
- arah flex berubah;
- child berpindah urutan;
- overlay berubah posisi;
- width berubah;
- padding berubah;
- elemen disembunyikan;
- elemen berubah dari absolute menjadi normal flow.

Dengan ini warning `register desktop/tablet/mobile` bisa diganti menjadi diagnosis yang jauh lebih spesifik.

7. Pembacaan asset dan URL

Mapper perlu membedakan:

- external HTTPS image;
- root-relative image;
- data URI;
- relative asset dalam ZIP;
- background image;
- image pada pseudo-element;
- SVG inline;
- icon font;
- local font.

Untuk local asset, widget sebenarnya sudah tersedia. Yang kurang adalah pipeline:

```text
source asset
→ asset manifest
→ File Manager mapping
→ persistent URL
→ widget setting
```

8. Pembacaan batas representasi Canvas

Setiap property perlu diklasifikasikan:

| Kategori | Tindakan |
|---|---|
| Native supported | Masukkan ke setting Canvas |
| Native supported responsive | Masukkan per viewport |
| Bisa direkonstruksi dengan Container | Buat nested structure |
| Bisa dipertahankan dengan Custom CSS | Simpan sebagai residual CSS |
| Membutuhkan asset mapping | Minta pemetaan asset |
| Benar-benar ambigu | Blocking + keputusan manual |

Jadi mapper tidak lagi memakai pendekatan:

```text
ada satu property sulit → seluruh section gagal
```

Melainkan:

```text
property A native
property B Custom CSS
property C asset mapping
property D blocking
```

Untuk `register`, kemungkinan hasil akhirnya akan seperti ini:

```text
Section register
├── Container root: native
├── Main layout: Grid/Container native
├── Heading: Heading widget
├── Description: Text Editor
├── CTA: Button
├── Poster image: Image/Image Box
├── Date badge: Container + Text/Heading
└── Decorative overlay: positioned Container atau scoped Custom CSS
```

Jadi ya, kita masih sangat bisa memperluas sistem pembacaan mapper. Bahkan arah terbaiknya bukan menambah aturan kecil satu per satu, tetapi mengubah mapper dari sekadar DOM-to-widget menjadi `evidence-driven visual layout graph`.

Batas realistisnya: tidak semua CSS dapat diterjemahkan 100% menjadi setting native. Tetapi untuk mayoritas layout website modern—Stack, Grid, Flex, nested Container, card, CTA, image overlay, icon box, responsive columns, padding, margin, border, dan positioning—jangkauannya masih dapat diperluas secara signifikan tanpa menambah widget baru atau menyentuh engine utama Page Builder.

## 2026-09-17 17:31:41 WIB — Laporan akhir assistant

**Sudah saya cek kedua tanggal di VPS dengan driver YOHANES YOPI DT-147. Penyebab utama hang berhasil teridentifikasi: proses pencocokan titik GPS ke jaringan jalan membebani thread utama browser selama puluhan detik.** Ini sudah didukung pengukuran runtime, bukan hanya dugaan dari source.

| Pengujian di VPS | 17 September 2026 | 15 September 2026 |
|---|---:|---:|
| Driver | YOHANES YOPI DT-147 | YOHANES YOPI DT-147 |
| Kegiatan | Angkut TBS | Angkut TBS |
| Durasi yang tampil | 0D 00H 17M | 0D 00H 11M |
| Distance yang tampil | 7087 KM | 810 KM |
| Titik GPS dalam respons | **965 titik** | **551 titik** |
| Respons rute selesai diterima | **1,35 detik** | **0,80 detik** |
| Waktu CPU pada proses snapping | **39,91 detik** | **20,66 detik** |
| Status API rute | HTTP 200 | HTTP 200 |

Angka waktu tersebut merupakan sampel diagnosis dengan profiler aktif; nilainya bisa berbeda antarperangkat. Namun, selisih antara waktu penerimaan data dan waktu komputasinya sangat jelas.

**Mengapa browser sampai terasa hang?**

Setelah menerima rute, fungsi `snapTripRouteToRoads()` mencoba menempelkan **setiap titik GPS ke seluruh 1.255 fitur jalan**, yang memuat **19.640 vertex**. Pencarian ini berjalan sinkron di thread yang juga menangani klik, scroll, dan pembaruan tampilan. Selama perhitungan berlangsung, browser kesulitan merespons interaksi.

Jalur tersebut ada pada [fungsi snapping](/D:/Laragon/www/laravel-13-cms-bum/public/assets/js/vuejs-v3-2024-dashboard.js:7124) dan dipanggil langsung dari [handler pilihan kegiatan](/D:/Laragon/www/laravel-13-cms-bum/public/assets/js/vuejs-v3-2024-dashboard.js:5474). Empat fungsi utama GOKUT yang saya bandingkan dari browser lokal dan VPS **identik setelah perbedaan akhir baris Windows/Linux diabaikan**.

Saya juga menemukan beberapa masalah yang memperburuk gejalanya:

- **Layer rute menumpuk.** Pada pengujian lokal, jumlah layer naik dari **6 menjadi 9** ketika rute dipilih ulang. Referensi layer diganti, tetapi layer lama tidak dihapus dari peta.
- **Ketika data tidak ditemukan, rute sebelumnya masih tertinggal.** Ini terverifikasi di lokal. Di VPS, kontrol kegiatan Jankos pada 15 September mengembalikan `Data route not found`; kasus kosong yang menyebabkan freeze total belum saya reproduksi secara terpisah.
- **Peta dipusatkan ulang untuk setiap potongan rute.** Pemanggilan `setView()` berada di `onEachFeature`, sehingga satu respons dapat memicu beberapa perubahan posisi peta. Ini kandidat penyebab loncatan visual, meskipun kontribusi waktunya belum diukur terpisah.
- **Ada error JavaScript lain di kedua situs:** `Cannot use import statement outside a module` dari paket Vue Datepicker. Error ini muncul sebelum memilih Angkut TBS; bukti profil CPU tetap menunjuk snapping sebagai penyebab utama freeze pada dua sampel tadi.

**Prioritas optimasi yang saya sarankan** adalah memperbaiki proses snapping terlebih dahulu: mempersempit kandidat jalan yang diperiksa dan menjalankan pekerjaan berat di luar thread UI, atau membaginya agar UI tetap mendapat kesempatan merespons. Setelah itu, gunakan satu layer rute aktif, bersihkan hasil lama ketika filter berubah/data kosong, dan sesuaikan posisi peta sekali setelah semua fitur siap. Menambahkan spinner saja tidak menyelesaikan pembekuan ini.

Ada juga temuan statis pada [controller GOKUT lokal](/D:/Laragon/www/laravel-13-cms-bum/app/Http/Controllers/Web/Dashboard/Dashboard_GOKUTController.php:166): filter driver pada query rute diterapkan ke relasi, sementara aktivitas induknya masih diambil lebih luas. Itu layak dioptimalkan, tetapi **belum saya pastikan terhadap source backend VPS**. Angka **7087 KM** juga baru saya cocokkan dengan tampilan Anda, belum saya nyatakan benar secara perhitungan bisnis.

## 2026-09-17 17:49:33 WIB — Laporan akhir assistant

**Arah yang paling tepat adalah memperbaiki pemrosesan rute di frontend terlebih dahulu, lalu merapikan pengelolaan peta dan request.** Dari pengujian tadi, API VPS selesai sekitar **0,8–1,35 detik**, sedangkan snapping menghabiskan **20–40 detik CPU browser**. Jadi prioritas pertama sudah jelas.

Saya menyarankan urutan berikut supaya perubahan tetap sempit dan manfaatnya bisa diukur.

**1. Buat proses snapping lebih ringan dan tidak membekukan browser.**

Ada dua pekerjaan yang saling melengkapi:

- **Persempit pencarian jalan.** Saat ini setiap titik GPS diperiksa terhadap seluruh jaringan jalan. Kita perlu menyiapkan indeks spasial sekali per estate, lalu hanya memeriksa segmen jalan di sekitar titik GPS. Batas snapping yang sekarang **200 meter** tetap dipertahankan agar perilaku tidak berubah tanpa alasan.
- **Pindahkan perhitungan berat ke Web Worker.** Dengan begitu, klik, scroll, dan pergantian filter tetap bisa berjalan selama rute dihitung. Worker cukup dibuat untuk tab GOKUT dan menggunakan kembali jaringan jalan serta indeksnya.

**Worker menjaga browser tetap responsif; indeks spasial mengurangi waktu perhitungannya.** Memindahkan algoritma lama ke worker saja masih bisa membuat pengguna menunggu lama, sedangkan optimasi pencarian tanpa memisahkannya dari thread UI masih berisiko membeku pada data besar.

Tidak perlu mengganti Leaflet atau menambah framework. Kita gunakan kemampuan browser dan komponen yang sudah tersedia sejauh mencukupi.

**2. Gunakan satu layer rute aktif dan satu kali pengaturan posisi peta.**

Alurnya perlu menjadi:

> Pilih filter → bersihkan rute lama → ambil dan proses data → pasang satu layer rute baru → sesuaikan posisi peta sekali.

Perubahan konkretnya:

- Hapus layer sebelumnya sebelum menggantinya.
- Saat driver, tanggal, atau kegiatan berubah, hasil lama tidak boleh terlihat sebagai hasil pilihan baru.
- Jika tidak ada data, peta tetap dapat digunakan dan menampilkan pesan **“Tidak ada rute untuk pilihan ini.”**
- Ganti `setView()` per fitur dengan satu `fitBounds()` setelah seluruh rute siap, mengikuti batas zoom peta.

Ini menangani penumpukan garis dan loncatan peta yang terpisah dari masalah CPU.

**3. Rapikan urutan request dan penanganan pergantian filter.**

Urutan yang efisien:

1. Pastikan driver, tanggal, dan kegiatan sudah dipilih.
2. Ambil data rute.
3. Jika rute kosong, selesai—tidak perlu mengambil atau memproses jaringan jalan.
4. Jika ada rute, gunakan jaringan jalan yang sudah dicache untuk estate tersebut.
5. Proses dan tampilkan hasil hanya jika filter masih sama.

Request sebelumnya perlu dibatalkan bila memungkinkan. Hasil worker juga harus memiliki penanda pekerjaan, sehingga hasil dari pilihan lama tidak bisa menimpa pilihan terbaru.

Indikator loading harus mencakup seluruh proses, termasuk snapping dan pemasangan rute. **Kontrol tetap responsif agar pengguna bisa mengganti pilihan**, bukan dikunci selama puluhan detik.

**4. Setelah jalur utama stabil, perbaiki beban tambahan yang sudah ditemukan.**

| Perbaikan lanjutan | Tujuan |
|---|---|
| Filter driver langsung pada query aktivitas induk | Menghindari pembacaan aktivitas dan lokasi driver lain |
| Hilangkan request ringkasan yang terpicu dua kali | Mengurangi pekerjaan server dan pembaruan UI |
| Periksa pemakaian Vue Datepicker, lalu hapus pemuatan yang tidak diperlukan atau perbaiki cara memuatnya | Menghilangkan error JavaScript yang sudah terkonfirmasi |
| Periksa perhitungan Duration/Distance secara terpisah | Memastikan angka seperti **7087 KM** benar untuk driver dan tanggal terpilih |

Pemeriksaan angka Distance sebaiknya dipisahkan dari optimasi rendering, karena menyangkut kebenaran hasil perhitungan. Jangan sampai masalah performa selesai tetapi angka dashboard masih mengambil data dengan cakupan yang salah.

**Cara mengerjakannya agar efisien:** implementasi di lokal dulu, dengan backup file terkait di `project-artifacts`, lalu uji fungsi snapping menggunakan data sintetis dan bandingkan hasil algoritma baru dengan algoritma lama. Sampel VPS yang sudah kita ukur menjadi acuan pengujian lanjutan setelah perubahan siap dan deployment diizinkan.

Kriteria penerimaannya:

- Klik, scroll, dan pergantian filter tetap merespons selama pemrosesan rute.
- Waktu snapping turun nyata pada data yang sama; target angkanya ditentukan dari pengukuran, bukan dijanjikan sebelum implementasi.
- Hasil snapping tetap konsisten dengan aturan jarak yang berlaku.
- Jumlah layer stabil meskipun kegiatan dipilih berulang kali.
- Data kosong membersihkan rute lama.
- Respons lama tidak menimpa filter terbaru.
- Kasus **YOHANES YOPI tanggal 15 dan 17 September** diuji kembali, termasuk di Firefox.

**Scope tahap pertama yang saya rekomendasikan: snapping dengan indeks spasial dan worker, satu layer rute aktif, serta pengendalian request/loading.** Ketiganya langsung menyasar penyebab hang dan glitch yang sudah terbukti. Source belum saya ubah.

## Rekomendasi: Row → Column → daftar Field

Gunakan mental model seperti Grid/Flexbox, tetapi tetap terisolasi di dalam widget Form:

```text
Form
└── Step
    ├── Row 1 — 2 columns
    │   ├── Column 1
    │   │   ├── Name
    │   │   └── Message
    │   └── Column 2
    │       ├── Email
    │       └── New Field
    ├── Row 2 — 1 column
    │   └── Column 1
    │       └── Drop field here
    └── Form Actions
        └── Submit
```

Schema sederhananya:

```js
row = {
    id: "row-1",
    columnCounts: {
        desktop: 2,
        tablet: 1,
        mobile: 1
    },
    columns: [
        {
            id: "column-1",
            items: [/* field sebanyak apa pun */]
        },
        {
            id: "column-2",
            items: [/* field sebanyak apa pun */]
        }
    ]
};
```

Perbedaannya: `items[]` tidak lagi maksimal satu field. Setiap column menjadi satu daftar Sortable vertikal yang permanen.

Perilaku drag menjadi deterministik:

- Drop ke column kosong: field dimasukkan ke sana.
- Drop di bawah field: field ditambahkan setelahnya.
- Drop di atas field: field disisipkan sebelumnya.
- Drag dalam column yang sama: reorder.
- Drag antar-column atau antar-row: pindahkan field.
- Tidak ada automatic swap sama sekali.
- Pada saat drag, tampil insertion line di atas atau bawah field yang dituju.
- Setiap column selalu memiliki trailing drop area di bagian bawah. Setelah terisi, drop area tersebut berpindah ke bawah dan tidak pernah hilang.
- Row kosong tetap mempunyai area `Drop field here`.
- Submit dipindahkan keluar dari Row dan menjadi footer `Form Actions` pada final step. Jadi Submit tidak lagi menghabiskan slot atau mengganggu drop target Row.
- `Row Span` tetap dapat dipakai sebagai pengaturan tinggi visual field, tetapi tidak lagi menentukan kapasitas atau keberadaan drop area.

Saat jumlah column dikurangi, field dari column yang dihapus dipindahkan ke column terdekat sambil mempertahankan urutan. Saat ditambah, column kosong baru langsung tersedia.

| Pendekatan | Hasil |
|---|---|
| Menambah spare cell terus-menerus | Cepat, tetapi target dan swap tetap membingungkan |
| Flat `row.items[]` dengan auto-flow | Ringkas, tetapi ambigu ketika ingin meletakkan field di bawah column tertentu |
| **Row → Column → `items[]` unlimited** | **Paling mirip Grid/Flexbox dan paling mudah dipahami** |

Saya merekomendasikan opsi ketiga: ubah internal Form menjadi `Row → Column → ordered fields`, hilangkan swap otomatis, buat drop target permanen, dan keluarkan Submit menjadi Form footer. Page-level Container/Grid/Flexbox dan node tree tidak perlu disentuh.

Belum ada source yang saya ubah pada tahap ini. Apakah arsitektur ini kita setujui sebagai pengganti sistem cell satu-field sekarang?

Rancangan yang saya rekomendasikan:

1. Row Span toolbar tetap `absolute`, tetapi sepenuhnya berada di dalam field: `top: 8px`, tanpa `translateY(-50%)`. Jadi tidak terpotong dan tidak menggeser elemen.

2. Area Drop Field:

   - Row kosong: selalu terlihat.
   - Row terisi: tersembunyi saat idle, tetapi drop target tetap aktif.
   - Saat drag dimulai atau cursor memasuki row: target muncul kembali secara halus.
   - Drop ke field tetap bisa reorder/swap sesuai posisi.

3. Step indicator dibuat sesuai perilaku resmi Elementor:

   - None
   - Text
   - Icon
   - Number
   - Progress Bar
   - Number & Text
   - Icon & Text

   Shape hanya memengaruhi Number/Icon. Setiap Step juga mendapatkan label dan icon masing-masing. Canvas, Blade, dan frontend runtime akan memakai renderer yang sama. Referensi: [Elementor Form Widget](https://elementor.com/help/form-widget/) dan [Multi-Step Forms](https://elementor.com/help/multi-step-forms/).

4. Canvas submit memakai endpoint draft khusus yang authenticated, CSRF-protected, dan rate-limited:

   - Mengirim setting Form terbaru yang belum di-Save.
   - Menggunakan `FormSubmissionHandler` yang sama.
   - Validation, Email, Email 2, Webhook, dan Collect benar-benar dijalankan.
   - Collect dari halaman `/create` ditandai sebagai editor-test tanpa menyimpan page.
   - Redirect tidak langsung meninggalkan editor; URL redirect ditampilkan pada success notice agar draft tidak hilang.
   - Canvas menampilkan status sending, success, validation error, atau action error.

Saya belum mengubah source pada balasan ini karena poin 4 perlu persetujuan terhadap efek eksternal nyata. Jika skema submission di atas sudah sesuai, jawab **“gas skema ini”** dan saya langsung implementasikan keempat poin dengan backup, TDD, build, focused tests, serta Browser QA.

## 2026-08-22 16:47:46 WIB — Laporan akhir assistant

Penyebabnya sudah terkonfirmasi: endpoint test Form di Canvas memang sengaja mewajibkan login, tetapi halaman editor v2.3 sendiri masih dapat dibuka tanpa login.

Alurnya:

1. Canvas menjalankan `submitFormDraft()` dan mengirim POST ke `/form/editor-draft` melalui [app.js](/D:/Laragon/www/laravel-13-phoenix/public/js/pagebuilder_elementor_v23/app.js:7377).
2. Endpoint tersebut memakai middleware `auth`, `checkSuspended`, dan throttle di [experimentalFeaturesWebv2.php](/D:/Laragon/www/laravel-13-phoenix/routes/experimentalFeaturesWebv2.php:48).
3. Session Firefox saat itu tidak dikenali sebagai user terautentikasi, sehingga request dihentikan middleware `auth` dengan 401 sebelum masuk ke controller.
4. Canvas kemudian menampilkan `message: "Unauthenticated."` melalui error handler di [Canvas.vue](/D:/Laragon/www/laravel-13-phoenix/public/js/pagebuilder_elementor_v23/widgets/pro/shared/Canvas.vue:3326).

Kenapa terasa membingungkan:

- Route `GET /pagebuilder-elementor/v2.3/create` tidak memakai middleware `auth`, jadi guest tetap dapat membuka dan memakai editor.
- Namun tombol Send memakai endpoint yang dilindungi `auth`.
- Indikator hijau “Saved” bukan bukti bahwa user sedang login.
- Ini bukan masalah CSRF. CSRF gagal menghasilkan 419, sedangkan screenshot menunjukkan 401. Token CSRF juga sudah dikirim.
- Form definition dan `Actions After Submit` belum sempat diproses karena request berhenti sebelum `submitEditorDraftForm()` dijalankan.
- Dua error `moz-extension://.../detector.js` berasal dari extension Firefox dan tidak menyebabkan 401.

Focused test mengonfirmasi kontrak tersebut: 5/5 lulus, termasuk test yang secara eksplisit mengharapkan guest memperoleh 401 dan user terautentikasi dapat menjalankan draft submission.

Rekomendasi saya:

- Lindungi seluruh editor v2.3 dengan `auth` + `checkSuspended`, sehingga user diarahkan login sebelum masuk editor.
- Tambahkan penanganan 401 yang menampilkan “Session expired or you are not logged in” alih-alih teks mentah `Unauthenticated`.
- Jangan menghapus `auth` dari draft endpoint. Payload draft dapat menjalankan Collect, Email, Email 2, Webhook, dan Redirect; membukanya untuk guest akan menjadi celah penyalahgunaan.

Belum ada source yang saya ubah pada diagnosis ini.

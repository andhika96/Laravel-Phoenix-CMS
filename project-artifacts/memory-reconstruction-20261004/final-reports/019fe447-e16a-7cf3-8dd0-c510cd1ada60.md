## 2026-08-09T04:25:34.023Z

Menurut saya, **parity ketat tetap arah terbaik**, tetapi implementasinya sebaiknya melalui **migrasi bertahap**, bukan mengganti struktur sekaligus.

Saat ini struktur v2.3 masih seperti ini:

`Container → columns[] internal → children[]`

Lebar disimpan pada `column.flexBasis`, lalu handle resize mengubah lebar dua slot bersebelahan. Itu terlihat di [definition.js](/D:/Laragon/www/laravel-13-phoenix/public/js/pagebuilder_elementor_v23/widgets/layout/container/definition.js:315), [app.js](/D:/Laragon/www/laravel-13-phoenix/public/js/pagebuilder_elementor_v23/app.js:2588), dan logika resize di [app.js](/D:/Laragon/www/laravel-13-phoenix/public/js/pagebuilder_elementor_v23/app.js:4666).

Pada model Elementor yang ketat, struktur idealnya:

`Parent Flex Container → Child Container → Widget`

Artinya:

- “Kolom” bukan slot internal lagi, tetapi **Container sungguhan**.
- Setiap child Container dapat dipilih, diduplikasi, dihapus, diberi Style/Advanced, responsive width, background, border, dan nested content.
- `Add Column` secara teknis berubah menjadi **Add Child Container**.
- Drag pada edge mengubah width/flex-basis milik child Container yang bersebelahan.
- Navigator, canvas, editor state, dan frontend memiliki struktur yang sama—tidak ada abstraksi kolom tersembunyi.

Rekomendasi implementasinya:

1. Editor dan frontend sementara dapat membaca dua format: `columns[]` lama dan child Containers baru.
2. Ketika halaman lama dibuka, `columns[]` dikonversi **di memory** menjadi child Containers tanpa langsung mengubah database.
3. Konversi baru disimpan ketika pengguna benar-benar menekan Save.
4. Container baru dan preset dua/tiga kolom langsung menghasilkan child Containers.
5. Edge resize menulis responsive width pada child Container, bukan lagi `column.flexBasis`.
6. Setelah migrasi stabil, jalur `columns[]` lama dapat dipensiunkan—jangan dipertahankan sebagai hybrid permanen.

Perbaikan Flexbox dan Grid yang baru selesai tidak sia-sia. Itu membuat schema lama stabil dan memberi kita baseline aman untuk adapter migrasi. Namun perubahan parity ketat ini tetap cukup besar karena menyentuh drag/drop, selection, undo/redo, duplicate, responsive state, saved JSON, dan frontend renderer.

Pertanyaan keputusan pertamanya: **apakah halaman v2.3 lama kita migrasikan otomatis secara transparan ketika pengguna menekan Save—ini rekomendasi saya—atau model child Container hanya berlaku untuk halaman baru sementara halaman lama tetap memakai struktur legacy?**

## 2026-08-09T04:28:10.078Z

Kita pilih pendekatan **strict parity bertahap**. Dua alternatif lainnya—rewrite sekaligus dan hybrid permanen—kita tinggalkan karena masing-masing terlalu berisiko dan terlalu mahal dirawat.

### Desain bagian 1: arsitektur data

Schema baru akan menjadikan child Container sebagai sumber kebenaran:

```text
Parent Flex Container
└── children[]
    ├── Child Container
    │   └── children[] → Widget
    └── Child Container
        └── children[] → Widget
```

Ketentuannya:

- Schema baru tidak membuat `columns[]` internal.
- Width, flex-basis, responsive width, Style, dan Advanced tersimpan pada masing-masing child Container.
- Flexbox dan Grid menggunakan daftar child yang sama. Mengubah `displayType` tidak mengubah atau memindahkan konten.
- Preset dua/tiga kolom membuat dua/tiga child Containers.
- `Add Column` pada UX menjadi penambahan child Container, meskipun label tombol bisa tetap “Add Column” agar mudah dipahami.

Untuk halaman lama:

1. Saat dibuka, adapter mendeteksi `columns[]`.
2. Setiap kolom dikonversi menjadi child Container **di memory**.
3. ID, isi widget, urutan, dan `flexBasis` lama dipertahankan.
4. Membuka halaman tidak mengubah database.
5. Schema baru hanya ditulis ketika pengguna menekan Save.
6. Frontend renderer sementara dapat membaca schema lama dan baru.
7. Setelah seluruh jalur stabil, dukungan editor untuk `columns[]` dapat dipensiunkan; renderer kompatibilitas tetap dipertahankan lebih lama.

Dengan struktur ini, Grid → Flexbox atau Flexbox → Grid tidak lagi perlu membuat, memangkas, atau memindahkan “kolom”. Parent hanya mengganti algoritma layout; child Containers dan seluruh isinya tetap utuh.

Belum ada kode yang saya ubah pada tahap diskusi ini. Apakah bagian arsitektur data ini sudah pas agar saya lanjutkan ke desain UX child Container, edge resize, dan pengaman migrasinya?

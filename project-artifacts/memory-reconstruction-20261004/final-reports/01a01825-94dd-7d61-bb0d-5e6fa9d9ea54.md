### Tujuan

Menambahkan kemampuan:

### Rekomendasi scope Fase 1

Conditional logic diterapkan pada field dalam satu widget Form, bukan pada dua widget Form terpisah.

Schema yang disarankan:

```js
conditionalLogic: {
    enabled: true,
    relation: "all",
    rules: [
        {
            fieldId: "jenis",
            operator: "equals",
            value: "b"
        }
    ]
}
```

Operator awal:

- `equals`
- `not_equals`
- `contains`
- `empty`
- `not_empty`

Field tanpa `conditionalLogic` tetap selalu terlihat.

### Rencana pekerjaan

1. Kunci schema dan aturan validasi kondisi.
2. Tambahkan UI Conditional Logic di repeater `Form Fields`:
   - Enable/disable.

   - Nilai pembanding.

4. Tambahkan evaluator frontend pada [`frontend-runtime.js`](/D:/Laragon/www/laravel-13-phoenix/public/js/pagebuilder_elementor_v23/frontend-runtime.js:911).

Perbandingannya:

- **JSON langsung di Settings modal**: praktis untuk paste/import dan cocok untuk data kecil atau custom, tetapi akan menggembungkan JSON page jika datanya besar dan sulit dipakai ulang.

```text
        ↓
Dependent Select pada widget Form
```

Jadi modal JSON tetap ada untuk kenyamanan admin, tetapi data besar tidak disimpan berulang di setiap widget. API digunakan untuk import atau sinkronisasi, bukan dipanggil setiap kali pengunjung mengisi Form.

Ya, sebaiknya kita buat **universal hierarchical dataset**, bukan khusus Negara/Provinsi. Keempat contoh Anda sebenarnya memakai pola yang sama:

```text
Parent → Children → Grandchildren
```

Jadi engine tidak perlu mengenal istilah Negara, Variant, atau Tipe.

### Proposal format JSON

Ini masih proposal, belum dikunci:

```json
{
  "schemaVersion": 1,
  "id": "dataset-location",
  "name": "Location Dataset",
  "levels": [
    { "id": "country", "label": "Country" },
    { "id": "province", "label": "Province" },
    { "id": "city", "label": "City" }
  ],
  "nodes": [
    {
      "id": "country-id",
      "label": "Indonesia",
      "name": "Indonesia",
      "code": "ID",
      "value": "ID",
      "kind": "country",
      "children": [
        {
          "id": "province-jabar",
          "label": "Jawa Barat",
          "name": "Jawa Barat",
          "code": "ID-JB",
          "value": "ID-JB",
          "kind": "province",
          "children": [
            {
              "id": "city-bandung",
              "label": "Bandung",
              "name": "Bandung",
              "code": "ID-JB-BDG",
              "value": "ID-JB-BDG",
              "kind": "city",
              "children": []
            }
          ]
        }
      ]
    }
  ]
}
```

Arti field:

- `id`: identitas internal yang stabil.
- `label`: teks yang tampil di select.
- `name`: nama resmi/canonical, opsional.
- `code`: kode dari sumber data.
- `value`: nilai yang dikirim saat submit.
- `kind`: tipe node, tetapi tidak wajib dibatasi.
- `children`: turunan node dengan kedalaman bebas.
- `meta`: bisa ditambahkan nanti untuk data tambahan.

Dengan model ini, semua pola berikut berjalan dengan engine yang sama:

- Negara → Provinsi → Kota.
- Variant A → Subvariant A.
- Tipe A → Subtipe A.
- Tipe/Variant → Subtipe/Subvariant → level berikutnya.

Untuk tiga widget di tiga halaman, setiap Form cukup menyimpan `datasetId`. JSON dataset tidak disalin ke setiap page. Jika dataset dibagikan, kita juga perlu fitur versioning atau clone agar perubahan global tidak mengejutkan widget lain.

Saya merekomendasikan format **nested dengan `children`** untuk JSON yang ditempel di modal karena paling mudah dibaca dan diedit. Namun ini belum saya anggap final.

Pertanyaan planning berikutnya: apakah format JSON modal ingin menggunakan struktur nested `children` seperti contoh ini, atau Anda lebih nyaman dengan format flat menggunakan `parentId`?

### Dua mode pengelolaan

**Visual Manager**

Untuk data kecil:

- Add Root Item.
- Add Child Item.
- Edit `label`, `name`, `code`, `value`, `kind`.
- Pilih `parentId`.
- Atur urutan dan status aktif.
- Delete atau pindahkan node.

Contohnya Variant 5 dapat dibuat lewat form, lalu ditambahkan 2–5 Subvariant di bawahnya.

**JSON Manager**

Untuk data besar:

- Paste atau import JSON melalui modal.
- Validate struktur.
- Tampilkan jumlah node, root, kedalaman, dan error.
- Preview hierarchy.
- Export kembali ke JSON.
- Simpan sebagai dataset reusable.

Kedua mode tersebut harus menggunakan normalizer dan validator yang sama agar hasilnya konsisten.

### Arsitektur pemakaian

```text
Dataset Manager
        ↓
Dataset tersimpan terpusat
        ↓
Widget Form memilih datasetId
        ↓
Field Parent → Field Child → Field Grandchild
```

Tiga widget di tiga halaman dapat memakai dataset yang sama tanpa menyalin JSON ke setiap page. Jika dataset diubah, sistem perlu memberi peringatan bahwa perubahan dapat memengaruhi semua widget yang menggunakannya.

Hal yang masih perlu dikunci sebelum planning final:

- JSON import mengganti seluruh dataset atau merge/upsert ke dataset lama.
- Penyimpanan dataset memakai JSON payload atau node database terpisah.
- Nilai submission memakai `id`, `code`, atau `value`.
- Apakah dataset dapat diedit oleh semua user atau hanya admin.
- Apakah API hanya untuk import/sync, bukan runtime.

Pertanyaan pertama yang paling penting: ketika dataset lama sudah berisi Variant 1–4 lalu Anda memasukkan JSON Variant 5, apakah perilakunya harus **mengganti seluruh dataset** atau **menambahkan/memperbarui node yang ada**?

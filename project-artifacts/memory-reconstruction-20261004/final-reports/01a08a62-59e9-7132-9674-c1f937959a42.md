
Artinya, status import sudah berhasil berubah menjadi `cancelled` di backend. Yang rusak adalah proses pembaruan DOM setelah respons diterima.

Saya sudah memperbaikinya.

### Root cause

Ada tiga kondisi yang bertabrakan:

1. Stepper menggunakan elemen dinamis:

   ```html
   <i v-if="..." class="fas fa-check"></i>
   ```

   Font Awesome otomatis mengganti `<i>` tersebut menjadi `<svg>` di luar kendali Vue. Saat cancel mengubah stepper dari tanda centang kembali menjadi angka, Vue mencoba memanipulasi node `<i>` yang sebenarnya sudah diganti. Inilah sumber utama error `insertBefore ... is null`.

   Pemeriksaan DOM sebelum perbaikan membuktikan isinya sudah berubah menjadi:

   ```html
   <svg data-icon="check">...</svg>
   <!-- <i class="fas fa-check"></i> Font Awesome -->
   ```

2. Polling status yang lama masih berjalan ketika request cancel dikirim. Setelah cancel berhasil, respons polling lama masih dapat tiba dan mencoba memperbarui status sebelumnya.

3. Cancel memulai request GET detail baru ketika Vue sedang melepas preview dan Leaflet masih memegang DOM map. Ini memicu pembaruan komponen bertumpuk dan menghasilkan error lanjutan `emitsOptions ... is null`.

### Perbaikan yang diterapkan

- Stepper sekarang memakai satu node `<span>` stabil:

  ```html
  {{ selesai ? '✓' : nomor }}
  ```

  Font Awesome tidak lagi mengganti node yang dikelola Vue.

- Sebelum commit, retry, atau cancel:

  - Polling terjadwal dihentikan.
  - Polling yang sedang berjalan di-abort.
  - Request detail lama di-abort.
  - `operationVersion` dinaikkan.

- Respons polling dan detail menyimpan versi operasinya. Respons lama otomatis diabaikan jika versi sudah berubah.

- Cancel tidak lagi memulai GET detail baru yang bersaing. Respons summary dari endpoint cancel sudah cukup untuk menampilkan status cancelled.

- Leaflet dibersihkan sebelum panel preview dilepas oleh Vue.

- State tombol langsung disesuaikan dari status server:

  - `cancelled` tidak memiliki tombol **Batalkan import**.
  - `completed` tidak memiliki tombol cancel.
  - `ready` tetap memiliki tombol commit.
  - `failed` memiliki tombol retry.

- Jika pekerjaan dibatalkan setelah file selesai dibaca, stepper tetap menunjukkan tahap **2. Periksa hasil**, bukan kembali ke tahap upload.

```json
   }
```

3. **Identitas berbeda tetapi polygon sama**
   - Klasifikasikan sebagai `geometry_conflict`.
   - Jangan langsung insert, karena satu polygon identik bisa diberi nama ancak atau blok yang berbeda akibat kesalahan atribut.

4. **Identitas dan polygon berbeda**
   - Insert sebagai data baru.

Masalah pentingnya adalah jika identitas seperti `R1 / BUM 1 / AFD 5 / E40 / ANCAK 1` sudah ada lalu polygon baru langsung ditambahkan, tabel dapat mempunyai dua batas aktif untuk ancak yang sama. Di tampilan peta keduanya bisa bertumpuk dan pengguna tidak tahu mana yang berlaku.

Karena itu, saya lebih menyarankan salah satu dari dua kebijakan berikut:

### Pilihan A — Versi geometri, direkomendasikan

Geometri baru disimpan sebagai versi terbaru untuk objek Batas Ancak yang sama:

- record lama tetap tersimpan sebagai histori;
- hanya satu versi berstatus aktif;
- geometri baru masuk sebagai versi pending atau aktif sesuai flow persetujuan;
- map utama hanya membaca versi aktif;
- histori tetap dapat dilihat;
- rollback ke geometri sebelumnya tetap mungkin.

Ini paling aman untuk data batas administratif atau operasional.

### Pilihan B — Insert sebagai record independen

Setiap polygon berbeda langsung menjadi baris baru:

- implementasinya lebih sederhana;
- berpotensi menghasilkan beberapa batas aktif dengan kombinasi region, estate, afdeling, block, dan ancak yang sama;
- query, filter, laporan, serta map harus siap menangani duplikasi identitas;
- pengguna harus membedakan record melalui ID atau nomor versi secara manual.

Pilihan B sesuai kalimat “geometry berbeda berarti insert baru”, tetapi risikonya cukup besar untuk data master. Saya merekomendasikan Pilihan A.

## Kebijakan untuk Pokok tidak boleh sama persis

Untuk data Pokok yang berjumlah lebih dari 2,5 juta:

- `UUID sama + koordinat sama` berarti duplikat, jadi jangan insert.
- `UUID sama + koordinat berbeda` lebih tepat berarti **lokasi pokok berubah** atau ada koreksi koordinat.
- Kondisi tersebut sebaiknya masuk sebagai **Penyesuaian Lokasi**, bukan membuat pohon kedua dengan UUID yang sama.
- `UUID berbeda + koordinat berbeda` berarti calon data baru.
- `UUID berbeda + koordinat sama atau sangat dekat` perlu ditandai sebagai potensi duplikat spasial.

Jika `UUID sama + koordinat berbeda` langsung menjadi insert baru, sistem bisa mempunyai dua pohon logis yang sebenarnya sama. Ini dapat memengaruhi:

- jumlah pokok;
- laporan produksi;
- perhitungan populasi;
- data Aresta;
- map;
- persetujuan;
- proses penghapusan atau pemindahan data berikutnya.

Karena halaman Pokok sudah mempunyai fungsi **Penyesuaian Lokasi**, fungsi tersebut merupakan jalur yang paling tepat untuk kasus koordinat berubah.

## Cara membuat `geometry_hash`

Geometri tidak boleh dibandingkan dari JSON mentah. Polygon yang sama bisa memiliki representasi JSON berbeda karena:

- titik awal ring berbeda;
- arah urutan koordinat terbalik;
- urutan polygon atau hole berbeda;
- jumlah digit desimal berbeda;
- terdapat titik berulang;
- format `Polygon` dan `MultiPolygon` berbeda walaupun secara visual sama.

Sebelum dihitung hash-nya, geometri perlu dikanonisasi.

Untuk Batas Ancak:

1. Konversi geometri ke EPSG:4326 seperti flow sekarang.
2. Bulatkan koordinat ke presisi yang disepakati.
3. Hapus vertex berurutan yang identik.
4. Pastikan ring tertutup.
5. Normalisasi arah ring.
6. Putar urutan ring agar dimulai dari koordinat terkecil yang konsisten.
7. Urutkan interior rings dan bagian `MultiPolygon`.
8. Serialisasi ke bentuk JSON atau binary yang stabil.
9. Hitung SHA-256 dari hasil canonical tersebut.

Dengan demikian, polygon yang sama tetapi urutan vertex-nya berbeda tetap mendapatkan `geometry_hash` yang sama.

Untuk Pokok:

1. Konversi ke longitude dan latitude.
2. Normalisasi tipe numeriknya.
3. Bulatkan ke presisi tertentu.
4. Hash pasangan `longitude|latitude`.

Untuk titik Pokok, presisi perlu disepakati:

| Presisi | Perkiraan di ekuator | Dampak |
|---|---:|---|
| 5 desimal | sekitar 1,1 meter | Lebih toleran terhadap perbedaan GPS kecil |
| 6 desimal | sekitar 11 sentimeter | Seimbang untuk pemetaan pohon |
| 7 desimal | sekitar 1,1 sentimeter | Hampir membandingkan koordinat secara eksak |

Saya cenderung memilih **6 desimal untuk fingerprint awal**, sementara deteksi “lokasi sangat dekat” dilakukan sebagai klasifikasi tambahan, bukan sebagai unique constraint.

## Supaya cepat untuk 2,5 juta data

Sistem tidak boleh mencari geometri dengan cara:

- membandingkan kolom JSON satu per satu;
- menjalankan query untuk setiap record;
- melakukan `ST_Equals` atau `ST_Distance` terhadap seluruh tabel;
- membaca semua 2,5 juta data ke PHP;
- memasukkan geometry JSON ke dalam `identity_hash`.

Strategi performanya:

### 1. Hitung hash saat geometri sedang dikonversi

Importer saat ini sudah membaca dan mengonversi setiap geometri. `geometry_hash` dihitung pada proses yang sama, sehingga SHP tidak perlu diparsing dua kali.

Alurnya:

```text
Baca record SHP
    ↓
Konversi CRS ke EPSG:4326
    ↓
Normalisasi geometri
    ↓
Hitung geometry_hash
    ↓
Kumpulkan satu batch
    ↓
Query fingerprint batch ke database
    ↓
Klasifikasikan record
```

### 2. Pemeriksaan dilakukan per batch

Misalnya satu batch berisi 500–2.000 record. Sistem menjalankan query seperti:

```sql
WHERE region = ?
AND identity_hash IN (...)
```

dan jika diperlukan:

```sql
WHERE region = ?
AND geometry_hash IN (...)
```

Hasilnya disusun menjadi map di memory PHP untuk batch tersebut. Ini menghindari masalah N+1 query.

### 3. Simpan hash dalam bentuk ringkas

Untuk jutaan baris, rekomendasi saya:

```sql
geometry_hash BINARY(32) NULL
```

`BINARY(32)` menyimpan SHA-256 dalam bentuk binary. Ukurannya setengah dari `CHAR(64)` hexadecimal, sehingga index lebih kecil.

Untuk tabel Pokok yang dipartisi berdasarkan region, index perlu mengikuti partition key, misalnya:

```sql
INDEX idx_pokok_region_geometry_hash (region, geometry_hash)
```

Kita tidak perlu membuat `geometry_hash` sebagai unique global. Pohon yang berdekatan atau data yang belum bersih dapat menimbulkan false positive jika hash memakai pembulatan koordinat.

### 4. Backfill terpisah dan resumable

Penambahan kolom ke 2,5 juta baris dan pengisian hash jangan dijalankan dalam satu migration besar. Pengalaman migration sebelumnya menunjukkan perubahan tabel besar bisa membutuhkan waktu lama di VPS.

Rencananya:

1. Migration hanya menambahkan kolom nullable dan index dengan strategi database yang mendukung operasi online.
2. Buat command atau queued job untuk backfill secara bertahap.
3. Gunakan `chunkById`.
4. Simpan checkpoint ID terakhir.
5. Proses dapat dilanjutkan jika worker berhenti.
6. Setiap chunk melakukan update batch.
7. Setelah cakupan backfill mencapai 100%, strict geometry duplicate checking diaktifkan.

Saat backfill belum selesai:

- row baru langsung mempunyai `geometry_hash`;
- row lama yang hash-nya masih `NULL` diperiksa melalui kandidat `identity_hash`;
- sistem tidak perlu scan seluruh tabel.

### 5. Tidak memakai query jarak sebagai filter utama

Untuk 2,5 juta data, query “cari semua pohon dalam radius X meter” tidak boleh menjadi jalur utama tanpa kolom spatial dan spatial index yang benar.

Versi pertama cukup menggunakan:

- stable UUID;
- `identity_hash`;
- normalized `geometry_hash`;
- query batch berbasis index.

Spatial proximity dapat ditambahkan nanti jika data aktual menunjukkan banyak duplikat akibat pergeseran GPS beberapa sentimeter atau meter. Ini menjaga implementasi awal tetap kecil dan terukur.

Koordinat dibandingkan setelah:

1. SHP dibaca.
2. CRS dikonversi ke EPSG:4326.
3. Longitude dan latitude divalidasi.
4. Longitude dan latitude dinormalisasi menjadi enam angka desimal.
5. SHA-256 dihitung dari koordinat yang sudah dinormalisasi.

Enam angka desimal setara sekitar 11 sentimeter di ekuator. Perbedaan yang lebih kecil dianggap koordinat sama. Perubahan yang lebih besar masuk sebagai Penyesuaian Lokasi jika UUID dan region tetap sama.

Tetapi ada konsekuensi karena `identity_hash` data lama masih `NULL`:

1. Unique index `identity_hash + region` belum melindungi data lama karena MySQL/MariaDB memperbolehkan banyak nilai `NULL` pada unique index.
2. Jalur insert lain yang tidak melewati importer masih dapat membuat UUID lama menjadi duplikat.
3. Pemeriksaan berbasis `identity_hash` belum bisa digunakan secara konsisten oleh semua modul.
4. Data lama dan data hasil import baru mempunyai tingkat perlindungan database yang berbeda.
5. Audit identitas seluruh master Pokok belum dapat dilakukan hanya dari index hash.

Karena itu, rekomendasi saya adalah menambahkan **backfill command khusus yang resumable**, kemudian menjalankannya terpisah dari migration dan terpisah dari worker `gis-imports`.

Rancangannya:

```text
Preflight UUID duplikat
    ↓
Proses per region/partisi
    ↓
Ambil rentang ID kecil
    ↓
Isi identity_hash dengan SQL SHA2
    ↓
Commit
    ↓
Simpan checkpoint
    ↓
Jeda singkat
    ↓
Lanjut sampai selesai
```

Formula hash harus sama dengan importer:

```php
hash(
    'sha256',
    $region.'|'.mb_strtoupper($uuidIncrement)
);
```

Versi SQL MariaDB-nya:

```sql
SHA2(
    CONCAT(region, '|', UPPER(uuid_increment)),
    256
)
```

Backfill sebaiknya mempunyai karakteristik berikut:

- proses berdasarkan `region` agar selaras dengan partisi `P1`, `P2`, dan `P3`;
- batch awal 5.000 record;

- hanya memproses `identity_hash IS NULL`;
- memiliki checkpoint region dan ID terakhir;
- aman dihentikan dengan `Ctrl+C`;
- dapat dilanjutkan tanpa mengulang data selesai;
- memiliki opsi `--dry-run`;
- mempunyai opsi `--region=R1`;
- mempunyai opsi `--batch=5000`;
- menampilkan kecepatan, jumlah berhasil, sisa, dan estimasi waktu;
- berhenti sebelum update apabila ditemukan UUID duplikat;
- tidak dijalankan oleh worker import biasa;
- tidak diletakkan di migration deployment;
- tidak mengubah `geometry`, koordinat, UUID, atau atribut Pokok lainnya.

## Pengaruh terhadap performa importer

Backfill ini membuat unique index `identity_hash + region` sekarang benar-benar melindungi **2.773.874 record lama**, selain data baru dari importer.

Importer tetap menggunakan pencarian UUID kandidat karena:

- pencarian UUID memakai index yang sudah ada;
- tabel dipartisi berdasarkan region;
- lookup batch 200 UUID memiliki median 6,22 ms pada database lokal;
- tidak perlu membaca 2,77 juta hash untuk setiap import;
- geometri hanya dibandingkan untuk kandidat UUID yang ditemukan.

`identity_hash` menjadi pengaman identitas database, sedangkan `uuid_increment` tetap menjadi jalur lookup cepat terhadap data lama dan kandidat import.

## Perlindungan setelah backfill

```text
    ↓
```

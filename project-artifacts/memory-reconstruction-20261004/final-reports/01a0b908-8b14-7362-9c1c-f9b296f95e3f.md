Jadi, dari sisi FK database saja, replacement tidak akan langsung mengubah isi tabel lain. Tetapi ada dua risiko utama.

1. Risiko parent–child internal

Jika Anda mengganti header P2H tetapi tidak mengganti/memetakan ulang `lr_form_p2h_details.form_p2h_id`, detail bisa menunjuk ke header yang salah atau tidak ada. Hal yang sama terjadi di PM10:

- `lr_form_pm10_details.form_pm10_id` harus cocok dengan `lr_form_pm10.id`.
- `lr_form_pm10_details.form_pm10_item_id` harus cocok dengan `lr_form_pm10_items.id`.
- `lr_form_pm10_items.form_pm10_activity_id` harus cocok dengan `lr_form_pm10_activities.id`.

Jangan memakai SQL `REPLACE INTO` untuk header P2H atau PM10. Di MySQL, `REPLACE` dapat melakukan pola **DELETE lalu INSERT** saat key berbenturan. Karena detail memiliki `ON DELETE CASCADE`, detail yang terhubung dapat ikut terhapus sebelum insert baru selesai.

2. Risiko mismatch dengan payroll, meskipun tidak ada FK

Ini yang paling penting. Source aktif menunjukkan `DriverPayrollService` mencari P2H dengan kombinasi:

```php
emp_code + vehicle_code + date
```

Kemudian nilai `lr_form_p2h.operated` digunakan untuk mengisi status P2H pada payroll. Saat P2H disimpan atau diubah lewat aplikasi/API, service P2H juga dapat menyimpan ulang `driver_payrolls.p2h_status`.

- `driver_payrolls` **tidak otomatis ikut diperbarui**, karena tidak ada trigger database untuk menjalankan service Laravel.

- PM10 juga dipakai dalam relasi Eloquent payroll melalui `emp_code`; meskipun tidak ditemukan update langsung ke payroll seperti P2H, penggantian data dapat membuat informasi PM10 yang ditampilkan untuk pekerja berubah.

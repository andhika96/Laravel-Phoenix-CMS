## 2026-08-15T16:15:32.794Z

Ya, ini kemungkinan besar masalah jalur scheduler yang berbeda antara Firefox dan Chrome, bukan error Video Playlist lagi.

Penyebab utama di source aktif:

1. `warmWidgetModules()` langsung memuat Canvas dan Settings saat `pointerdown`. Di Firefox, proses compile SFC dapat masih berjalan ketika Anda mulai mengetik.

2. Setelah gesture pertama, `scheduleWidgetSettingsPreloadAfterFirstGesture()` masih melakukan preload shared controls melalui `requestIdleCallback()`.

3. Guard input hanya mengandalkan:

```js
navigator.scheduling?.isInputPending?.(...)
```

Firefox umumnya tidak menyediakan API ini, sehingga hasil optional chaining menjadi `undefined` dan dianggap tidak ada input aktif. Akibatnya preload tetap berjalan ketika Anda sedang mengetik. API tersebut memang masih eksperimental/deprecated dan tidak boleh menjadi satu-satunya pengaman scheduling. [MDN isInputPending](https://developer.mozilla.org/en-US/docs/Web/API/Scheduling/isInputPending)

`requestIdleCallback()` juga tetap menjalankan pekerjaan di main thread; pekerjaan compile SFC yang berat bisa memblokir input. [MDN requestIdleCallback](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestIdleCallback)

Selain itu, deep watcher `rootNodes` masih melakukan traversal layout setiap perubahan setting di [app.js](D:/Laragon/www/laravel-13-phoenix/public/js/pagebuilder_elementor_v23/app.js:3928). Debounce sebelumnya hanya menunda `JSON.stringify`, bukan menghilangkan traversal Vue.

Jadi Chrome terasa aman karena scheduler dan engine JavaScript-nya lebih cepat, sedangkan Firefox memperlihatkan beban preload/compile tersebut.

Solusi paling tepat berikutnya adalah menghapus preload shared controls setelah gesture pertama, lalu memakai fallback scheduler berbasis aktivitas pointer/keyboard yang berlaku sama di semua browser. Saya belum mengubah source pada turn ini karena Anda sedang menanyakan penyebabnya terlebih dahulu.
